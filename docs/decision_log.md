## D-001 交付形态与放置位置（2026-10-05）
- 背景：需要把本项目验证过的"文档驱动 AI 编码"体系提炼为通用工作流，供 zcode 及其他 CLI 编码代理使用。
- 选项：
  - A. 纯 Markdown 方法论包——优点：agent 无关、零依赖、可入库；缺点：逐段手动复制提示词。代价：无。
  - B. 仅 ZCode Skill——优点：一键触发；缺点：绑死 zcode，其他 agent 不可用。代价：中。
  - C. A+B 混合：Markdown 唯一事实源 + Skill 轻量入口壳（引用不复制）——优点：通用底座+zcode 加速；缺点：两个入口需一致（skill 只引用）。代价：中。选。
  - D. 完整 Plugin（skill+command+hooks）——优点：自动化最深；缺点：hooks 绑 zcode 且破坏 agent 无关性。代价：高。弃。
- 位置候选：本仓库 docs/ 下（与产品混库，弃）；用户级 ~/.zcode/（脱离版本管理，弃）；**独立新仓库 `~/proj/agent_dev_kit/`（git init，选）**。
- 结论：C + 独立新仓库。
- 理由：用户明确要求"zcode 或其他 agent code"通用；横切方法论资产不应长在产品仓库里。
- 影响：全部交付物落 agent_dev_kit 仓库；本项目 design_docs/ 作为填好的实例被引用。

## D-002 CI/CD 硬要求（2026-10-05）
- 背景：用户要求所有项目最终必须 GitHub CI 构建成功+测试通过，tag 触发上传二进制到 Release，重型构建环境启用缓存。本项目 T0.3/T7.2/10§4 已有实证模式。
- 选项：
  - A. CI 作为可选建议——缺点：不满足"必须构建成功"的硬诉求。弃。
  - B. CI/CD 作为强制条款写入方法学：里程碑验收=本地质量门+GitHub CI 全绿；M0 必含 CI 骨架任务；release.yml 由 tags v* 触发（矩阵构建→artifact→汇总 Draft Release 上传二进制）；缓存强制且 key 随锁文件失效——优点：与本项目实证对齐、跨栈可泛化；缺点：小项目也需 CI。代价：低（XS 档仍保留 CI）。选。
  - C. 自建 CI 抽象层/脚本生成器——优点：更自动；缺点：绑栈、维护重。代价：高。弃。
- 结论：B。
- 影响：AGENTS.md 规范条款、ci.yml/release.yml 模板（含 Go/Node/Python/Rust 缓存变体注释）、路线图模板 CI/CD 节、纠偏表。

## D-003 图表规范与开发模式（2026-10-05）
- 背景：用户要求各阶段文档必须含足够清晰的设计图（mermaid 优先、plantuml 候选），以软件工程生命周期为参照支持瀑布/螺旋/敏捷等模式，核心算法必配完整流程图、核心通信必配数据交互图。
- 选项：
  - A. 仅 mermaid——优点：GitHub 原生渲染零环境；缺点：用例图/部署图/泳道活动图等 OO 强项缺失。代价：低。弃（单选）。
  - B. mermaid 优先 + plantuml 候选（用例图、部署图、泳道活动图、复杂类图四类收编 plantuml，选用记 DR）——优点：覆盖全、渲染分场合；缺点：plantuml 需渲染环境。代价：低。选。
  - C. 每项目自选任意工具——优点：自由；缺点：不可机检、不统一。弃。
- 强制图定档：18 张强制（上下文图/分层架构/模块依赖/DFD 0-1 级/用例图/实体状态图/核心算法流程图/数据交互时序图/ER·类图/状态机图/测试金字塔/CI 流水线/里程碑 DAG/gitGraph 分支模型/部署图/发布流水线/会话执行循环/验收状态机/缺陷流转）+ 8 张条件触发（业务流程/用户旅程/故事地图/敏感数据流/泳道活动/包组件/测试环境拓扑/迁移回滚路径；未触发也写判定结论）。
- 开发模式：瀑布（默认基线=本流程原生）/螺旋（风险驱动多轮细化）/敏捷（轻量文档+迭代同步），三档共用模板。
- 结论：B + 18+8 强制条件清单 + 三模式适配。
- 影响：WORKFLOW 图表总表、全部设计文档模板"必备图"段、P2 生成提示词、复审图文一致性检查。

## D-004 规模分级与裁剪（2026-10-05，后经 D-010 扩为四档连续谱）
- 背景：全套体系对小项目过度工程，需要裁剪阀门。
- 选项：
  - A. 不分级，全量套用——缺点：小项目被吓退。弃。
  - B. S/M/L 三档（S 级：领域≤3、强制图减至 6 张、领域设计可合并）——优点：体系内可裁；缺点：仍不覆盖"不该用整套"的场景。代价：低。并入 C。
  - C. XS（Lite 路径，见 D-010）/S/M/L 四档连续谱+裁剪规则表+模板条件段标注——优点：从"不该用"到"全量"连续覆盖。代价：中。选。
- 结论：C。
- 影响：WORKFLOW §0/裁剪规则表、lite/ 模板、LITE.md、P0 判定树。

## D-005 使用者与协作规模（2026-10-05）
- 背景：执行模型隐含单人假设，需明确团队场景。
- 选项：
  - A. 纯个人假设——优点：最简；缺点：团队无法直接用。弃。
  - B. 个人为主+团队适配注记（PR 评审辅助手测门、分支保护、任务认领与并行约束，约 30 行）——优点：主路径不变、成本可控；缺点：两路径需保持一致。代价：低。选。
  - C. 个人/团队完整双轨——优点：团队开箱即用；缺点：文档量近翻倍、双轨漂移。代价：中高。弃。
- 结论：B。
- 影响：WORKFLOW 执行模型节+执行手册模板"团队注记"节。

## D-006 人机驱动方式（2026-10-05）
- 背景：用户跳过此维度的选择，按已定案最小延伸处理。
- 选项：
  - A. 手动逐段复制提示词（当前定案）——优点：agent 无关最大化、全程掌控；缺点：操作繁琐。代价：无。
  - B. skill 升级为阶段引导器（按判定树自动输出提示词、门上暂停）——优点：省粘贴；缺点：维护成本、逻辑绑 zcode。代价：中。
  - C. 全自动流水线——与 P0 访谈的对话本质冲突，弃。
- 结论：折中——Markdown 手动主路径不变；skill=轻量阶段引导（列阶段序列、指引到对应提示词文件；不自动编排、不静默全自动，边界写入 SKILL.md）。
- 影响：SKILL.md、README 安装说明。

## D-007 套件质量验证（2026-10-05）
- 背景：30+ 条提示词从未执行过，可用性零验证是最大风险。
- 选项：
  - A. 不试运行——缺点：第一个真实用户即踩坑者。弃。
  - B. 小样例试运行：虚构"Markdown 笔记应用"（人为指定档位以覆盖两条路径）临时目录走全套档 P0→G2 + Lite 档两段提示词；干跑 P4.6 对账/P4.7 CR 输出格式；据发现修正提示词，产物收录 examples——优点：验证自含性与判定树、补绿地实例；缺点：多一轮工作量。代价：中。选。
  - C. 反向审计本项目——只能测重写形态。弃。
- 结论：B。
- 影响：实施步骤第 8 步、examples.md、提示词修正 commit。

## D-008 kit 自身工程化（2026-10-05）
- 背景：纯 Markdown 的一致性（引用闭合/条款齐全）靠人工必漂移；kit 自己应吃狗粮。
- 选项：
  - A. 零脚本——缺点：必漂移。弃。
  - B. 零依赖校验脚本 tools/check.mjs（"文件×必含标记"grep 级规则表，外置 checks 清单）+ kit 仓库自身 ci.yml（check.mjs+actionlint）——优点：轻、可维护、ci.yml 模板多一个活实例；缺点：语法类检查需让位（actionlint/GitHub 预览）。代价：中低。选。
  - C. ZCode hooks 强制——绑 zcode、侵入用户环境。弃。
- 结论：B。
- 影响：tools/、.github/workflows/ci.yml、check.mjs 规则清单。

## D-009 GUI 测试分层与手测方案（2026-10-05）
- 背景：用户要求 GUI 项目必须先在支持的自动化 GUI 测试框架中通过再人工手测，且必须给出完整手测方案防遗漏防偷懒。本项目实证：浏览器 mock 模式+Playwright、PROGRESS 手测指引分组、防错清单。
- 选项：
  - A. 仅人工手测——缺点：遗漏/偷懒、bug 修复延迟成本高。弃。
  - B. 强制分层：原生自动化框架优先（Electron→Playwright、Flutter→integration_test、Qt→pytest-qt 等）→ 原生窗口难自动化的用浏览器 mock 模式+Web 自动化框架（Wails 等）→ 确无框架记 DR+风险表登记+手测加厚；自动化全绿后才生成手测方案交人工——优点：与实证对齐、机器先行；缺点：无框架场景需兜底。代价：中。选。
  - C. 只强化手测清单不做自动化先行——缺点：违背用户硬要求。弃。
- 手测方案六节硬规格：环境准备/分组用例表（Step 编号+预期+⬜勾选+MT 编号）/覆盖映射（←需求编号+自动化未覆盖原因）/"预期已知行为（非 bug）"/缺陷记录格式/全勾选禁跳过。
- 结论：B+六节规格；每里程碑 docs/手测方案-M<N>.md。
- 影响：AGENTS.md 规范条款、测试方案模板 GUI 分层节、00 模板 mock 模式条件段、手测方案模板、P4 收尾句、纠偏表。

## D-010 适用边界与 Lite 档（2026-10-05）
- 背景：用户问"什么规模的项目适用？太小太简单用它反而笨重"——体系缺"不该用"的判据。
- 选项：
  - A. 不设边界——缺点：hammer for every nail。弃。
  - B. 四信号前置判定（领域子系统数/预计会话数/协议面与行为保真诉求/交付形态）→ 不适用（一次性脚本、spike、纯探索、纯文档任务→直接开干）/XS=Lite 三件套（需求与方案合一+AGENTS.md+CI 模板、核心图 2 张、无里程碑制、验收清单、真分歧才记 DR）/S/M/L；硬性例外：重写迁移无论多小≥S 档（保真机制不可省）、有发布诉求至少 Lite+CI——优点：连续谱+反模式清单防误用。代价：低。选。
  - C. 只写适用性说明不建 Lite 路径——缺点：小项目用户没有出路。弃。
- 结论：B。
- 影响：WORKFLOW §0、LITE.md、lite/ 模板、LITE 提示词、P0 判定树、README 速查。

## D-011 需求稳定性机制与前置保证（2026-10-05）
- 背景：用户问"拆解需求的注意事项/前置保证，例如需求不稳定"。文档驱动体系对需求中途变化最敏感（文档/代码/测试三处同步漂移）。
- 选项：
  - A. 不做机制，靠自觉——弃。
  - B. 全套机制：G0=需求基线冻结门；变更三类分流（bug→修复流程/范围变更→CR/方向变更→回 P0）；P4 执行期禁插需求→停车场 backlog.md；假设台账 assumptions.md 逐门复核、证伪即 CR；P0 访谈七纪律（可验收性硬判据/原子性/非目标成文/不确定显式化/禁发明需求/术语表先行/档位诚实）；前置保证四项（基线冻结/决策可用性=拍不了板用代理推荐+否决制/锚点资产可用/环境预检）；反幻觉锚点（一切事实有出处，无锚点标"待确认"）；《项目画像》一次成型后续只引用不重判——优点：直击三处同步漂移根因；缺点：流程纪律变重。代价：中。选。
- 结论：B。
- 影响：WORKFLOW 需求稳定性节、backlog/assumptions 模板、P0.1/P4.7 提示词、纠偏表、M0 T0.0 环境预检。

- 选项：
  - A. 各文件各自成文——缺点：演进必漂移。弃。

- 结论：B。
- 影响：AGENTS.md 模板结构、全部提示词/模板/WORKFLOW 的引用方式、check.mjs 规则。
